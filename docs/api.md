# 8.6. API-контракт

## Общие правила

- Базовый адрес — `/api`, локально `http://localhost:8000/api`, как в `frontend/src/api/axios.js`.
- Тело запросов и ответов — JSON, поля в `camelCase`. Идентификаторы — UUID, даты — ISO 8601 в UTC.
- Все методы, кроме регистрации и входа, требуют заголовок `Authorization: Bearer <accessToken>`.
- Ошибки возвращаются в одном формате. Фронт уже читает текст ошибки из `error.message`:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте введённые данные",
    "details": { "fields": { "password": "Нужна хотя бы одна цифра" } }
  }
}
```

| Код | Когда |
| --- | --- |
| 200 / 201 / 204 | Успех / создан ресурс / успех без тела |
| 400 | Неверные входные данные |
| 401 | Нет токена, он истёк, отозван или неверный; неверный email или пароль при входе |
| 403 | Чужое интервью ([Вопрос 8](#вопросы-к-команде)) |
| 404 | Ресурс не найден |
| 409 | Действие недопустимо в текущем состоянии, email занят |
| 500 | Внутренняя ошибка; подробности наружу не отдаются |
| 503 | LLM недоступна, и продолжить без неё нельзя |

## Авторизация на JWT

- Access token в формате JWT, подпись HS256, срок жизни — 60 минут. Refresh token в MVP нет.
- Секрет и срок — в переменных окружения `JWT_SECRET` и `JWT_EXPIRES_MINUTES`, в репозитории их нет.
- В токене: `sub` — id пользователя, `jti` — уникальный id токена, `iat` — время выдачи, `exp` — время окончания. Email и ФИО в токен не кладём: JWT читается без ключа.
- Проверка на каждом защищённом запросе; любая неудача — `401 UNAUTHORIZED`:
    1. Заголовок `Authorization: Bearer ...` есть.
    2. Подпись верна, срок не истёк.
    3. `jti` нет в `revoked_tokens` — токен не отозван выходом.
    4. Пользователь существует (не удалён).
    5. `iat` не раньше `users.password_changed_at` — токены, выданные до смены пароля, не работают.
- На Django удобно взять `djangorestframework-simplejwt` для выдачи токена, а проверки 3–5 добавить в свой класс аутентификации.

## Правила пароля

По FR-5.1.4: от 8 до 30 символов, хотя бы одна заглавная латинская буква, одна строчная латинская буква и одна цифра. Применяются при регистрации и смене пароля.

## Авторизация и профиль

### POST /api/auth/register

- **Назначение:** регистрация нового пользователя (UC-001).
- **Авторизация:** не нужна.

**Параметры запроса**

| Поле | Тип | Обязательное | Правила |
| --- | --- | --- | --- |
| `fullName` | string | Да | От 2 до 150 символов после обрезки пробелов |
| `email` | string | Да | Формат email, до 255 символов; обрезать пробелы, привести к нижнему регистру |
| `password` | string | Да | [Правила пароля](#правила-пароля) |

**Пример запроса**

```json
{ "fullName": "Иванов Иван Иванович", "email": "ivanov@example.com", "password": "Secret123" }
```

**Пример ответа — 201.** Токен не выдаётся: после регистрации фронт открывает экран входа, как уже сделано в `RegisterPage.jsx`.

```json
{
  "user": {
    "id": "6f1c2b0e-8a3d-4c1e-9d4f-2a7b5c9e1f30",
    "email": "ivanov@example.com",
    "fullName": "Иванов Иван Иванович",
    "createdAt": "2026-11-05T10:00:00Z"
  }
}
```

**Коды ошибок**

| Код | `error.code` | `message` | Когда |
| --- | --- | --- | --- |
| 400 | `VALIDATION_ERROR` | «Проверьте введённые данные» | Поле пустое или не по правилам; поля с ошибками — в `details.fields` |
| 409 | `EMAIL_ALREADY_EXISTS` | «Пользователь с таким email уже существует» | Email занят (FR-5.1.3) |

**Что сохраняется:** запись в `users`: ФИО, email в нижнем регистре, хеш пароля; `created_at` и `password_changed_at` — текущее время.

**Логика backend**

1. Обрезать пробелы у `fullName` и `email`, `email` привести к нижнему регистру. Пароль не изменять.
2. Проверить все поля и вернуть ошибки по всем сразу — `400 VALIDATION_ERROR`.
3. Если email уже есть в `users` — `409 EMAIL_ALREADY_EXISTS`.
4. Захешировать пароль, создать пользователя. Если сработал уникальный индекс по email (два запроса одновременно) — тоже `409`.
5. Вернуть `201`. Пароль и хеш в ответ и в логи не попадают.

### POST /api/auth/login

- **Назначение:** вход и выдача токена (UC-002).
- **Авторизация:** не нужна.

**Параметры запроса:** `email` (string, обязательное) и `password` (string, обязательное).

**Пример запроса**

```json
{ "email": "ivanov@example.com", "password": "Secret123" }
```

**Пример ответа — 200**

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "tokenType": "Bearer",
  "expiresIn": 3600,
  "user": { "id": "6f1c2b0e-8a3d-4c1e-9d4f-2a7b5c9e1f30", "email": "ivanov@example.com", "fullName": "Иванов Иван Иванович" }
}
```

Первые три поля — формат из ТЗ, `user` нужен фронту, чтобы сразу показать имя. В моке фронта токен лежит в поле `token` — Владу нужно брать его из `accessToken`.

**Коды ошибок**

| Код | `error.code` | `message` | Когда |
| --- | --- | --- | --- |
| 400 | `VALIDATION_ERROR` | «Заполните все поля» | Нет email или пароля |
| 401 | `INVALID_CREDENTIALS` | «Неверный email или пароль» | Пользователь не найден или пароль не подходит (FR-5.2.2) |

**Что сохраняется:** ничего; выданные токены в базе не хранятся.

**Логика backend**

1. Обрезать пробелы у email, привести к нижнему регистру; проверить, что оба поля не пустые.
2. Найти пользователя по email и проверить пароль. Если пользователь не найден или пароль не подходит, ответ одинаковый — `401 INVALID_CREDENTIALS`: так нельзя узнать, зарегистрирован ли email.
3. Выдать JWT: `sub` — id пользователя, новый `jti`, `iat` — сейчас, `exp` — через 60 минут.
4. Вернуть `200`.

### POST /api/auth/logout

- **Назначение:** выход с отзывом токена (UC-007).
- **Авторизация:** нужна.
- **Параметры запроса:** нет, только заголовок с токеном.
- **Пример ответа:** `204`, без тела.
- **Коды ошибок:** `401 UNAUTHORIZED` — токен уже недействителен. На любой ответ фронт удаляет токен и открывает экран входа.
- **Что сохраняется:** запись в `revoked_tokens`: `jti`, `user_id`, `expires_at` из токена и время выхода.

**Логика backend**

1. Проверить токен.
2. Добавить `jti` в `revoked_tokens`; если запись уже есть — ничего не делать.
3. Вернуть `204`. Записи с истёкшим `expires_at` можно периодически удалять.

### GET /api/users/me

- **Назначение:** данные текущего пользователя. Фронт вызывает его при загрузке приложения, чтобы убедиться, что сохранённый токен ещё действует.
- **Авторизация:** нужна.
- **Пример ответа — 200:**

```json
{ "id": "6f1c2b0e-8a3d-4c1e-9d4f-2a7b5c9e1f30", "email": "ivanov@example.com", "fullName": "Иванов Иван Иванович", "createdAt": "2026-11-05T10:00:00Z" }
```

- **Коды ошибок:** `401 UNAUTHORIZED`.
- **Логика backend:** проверить токен, вернуть данные из `users`; хеш пароля не отдавать.

### PUT /api/users/me/password

- **Назначение:** смена пароля (UC-009).
- **Авторизация:** нужна.

**Параметры запроса**

| Поле | Тип | Обязательное | Правила |
| --- | --- | --- | --- |
| `currentPassword` | string | Да | Текущий пароль |
| `newPassword` | string | Да | [Правила пароля](#правила-пароля), не совпадает с текущим |

**Пример запроса**

```json
{ "currentPassword": "Secret123", "newPassword": "NewSecret456" }
```

**Пример ответа — 200.** После смены пароля старые токены перестают работать на всех устройствах, поэтому в ответе — новый токен для текущего устройства.

```json
{ "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...", "tokenType": "Bearer", "expiresIn": 3600 }
```

**Коды ошибок**

| Код | `error.code` | `message` | Когда |
| --- | --- | --- | --- |
| 400 | `VALIDATION_ERROR` | «Проверьте введённые данные» | Новый пароль не по правилам |
| 400 | `INVALID_CURRENT_PASSWORD` | «Текущий пароль указан неверно» | Текущий пароль не совпал |
| 400 | `SAME_PASSWORD` | «Новый пароль совпадает с текущим» | Пароли одинаковые |
| 401 | `UNAUTHORIZED` | «Требуется авторизация» | Токен недействителен |

Неверный текущий пароль — это `400`, а не `401`: иначе фронт решит, что сессия закончилась, и выкинет пользователя на экран входа.

**Что сохраняется:** в `users` — новый хеш пароля и `password_changed_at`, округлённое до секунды.

**Логика backend**

1. Проверить токен и поля запроса.
2. Проверить текущий пароль; не подходит — `400 INVALID_CURRENT_PASSWORD`. Новый совпадает с текущим — `400 SAME_PASSWORD`.
3. Сохранить новый хеш и `password_changed_at` = сейчас, округлённое до секунды. С этого момента старые токены не проходят проверку.
4. Выдать новый токен с `iat` = `password_changed_at` и вернуть `200`. Округление нужно, потому что `iat` в JWT хранится в секундах: без него новый токен окажется «старше» смены пароля.

### DELETE /api/users/me

- **Назначение:** удаление профиля и всех данных пользователя (UC-010, FR-5.10.3).
- **Авторизация:** нужна.
- **Параметры запроса:** `password` (string, обязательное) — подтверждение паролем.
- **Пример запроса:** `{ "password": "Secret123" }`
- **Пример ответа:** `204`, без тела. Фронт удаляет токен и открывает экран входа.

**Коды ошибок**

| Код | `error.code` | `message` | Когда |
| --- | --- | --- | --- |
| 400 | `INVALID_PASSWORD` | «Пароль указан неверно» | Пароль не совпал; ничего не удаляется |
| 401 | `UNAUTHORIZED` | «Требуется авторизация» | Токен недействителен |

**Что удаляется:** запись в `users` и каскадно — интервью, вопросы интервью, ответы, итоговые рекомендации и отозванные токены пользователя.

**Логика backend**

1. Проверить токен и пароль; не совпал — `400 INVALID_PASSWORD`.
2. В одной транзакции удалить пользователя; связанные данные удаляются каскадно.
3. Вернуть `204`. Все токены пользователя после этого не проходят проверку: пользователя больше нет.

## Интервью

Для всех методов с `{id}` интервью — общая **проверка доступа**:

1. Проверить токен; не прошёл — `401 UNAUTHORIZED`.
2. Найти интервью; нет или `id` не UUID — `404 INTERVIEW_NOT_FOUND`.
3. Интервью другого пользователя — `403 FORBIDDEN` (FR-5.10.1).

### GET /api/directions

- **Назначение:** позиции и уровни для экрана настройки интервью (UC-003).
- **Авторизация:** нужна.
- **Пример ответа — 200:**

```json
{
  "directions": [ { "code": "backend_python", "name": "Backend-разработка (Python)", "description": "ООП, SQL, REST API" } ],
  "levels": [
    { "code": "junior", "name": "Junior", "description": "Основы и применение на простых примерах" },
    { "code": "middle", "name": "Middle", "description": "Сравнение подходов и обоснование выбора" }
  ]
}
```

- **Логика backend:** вернуть активные позиции и уровни, отсортированные по `sort_order`. Справочники заполняются миграцией.

### POST /api/interviews

- **Назначение:** создать интервью из 5 вопросов (UC-003, FR-5.4.1 – FR-5.4.3).
- **Авторизация:** нужна.

**Параметры запроса**

| Поле | Тип | Обязательное | Правила |
| --- | --- | --- | --- |
| `directionCode` | string | Да | Активная позиция из справочника |
| `levelCode` | string | Да | `junior` или `middle` |

**Пример запроса**

```json
{ "directionCode": "backend_python", "levelCode": "junior" }
```

**Пример ответа — 201**

```json
{ "id": "6f1c2b0e-8a3d-4c1e-9d4f-2a7b5c9e1f30", "status": "CREATED", "directionCode": "backend_python", "levelCode": "junior", "totalQuestions": 5, "createdAt": "2026-11-05T10:30:00Z" }
```

**Коды ошибок**

| Код | `error.code` | Когда |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR`, `UNKNOWN_DIRECTION`, `UNKNOWN_LEVEL` | Нет полей или значения нет в справочнике |
| 409 | `ACTIVE_INTERVIEW_EXISTS` | Уже есть незавершённое интервью; его id — в `details.interviewId` ([Вопрос 3](#вопросы-к-команде)) |
| 503 | `QUESTIONS_UNAVAILABLE` | LLM недоступна, а в базе меньше 5 вопросов |

**Что сохраняется:** 5 вопросов в `questions` с `source = LLM`, запись в `interviews` со статусом `CREATED`, 5 записей в `interview_questions`.

**Логика backend**

1. Проверить токен, позицию и уровень.
2. Если у пользователя есть интервью в статусе `CREATED` или `IN_PROGRESS` — `409` ([Вопрос 3](#вопросы-к-команде)).
3. Взять из базы до 10 случайных активных вопросов этой позиции и уровня — они идут в запрос к LLM как примеры (FR-5.4.1).
4. Попросить LLM сгенерировать 5 вопросов. Проверить ответ: ровно 5 непустых вопросов, без повторов (FR-5.4.2, FR-5.4.3).
5. Если LLM не ответила или ответ не прошёл проверку — один повтор. Снова неудача — взять 5 случайных вопросов из базы [Предложение]. Если в базе их меньше 5 — `503`.
6. В одной транзакции сохранить вопросы, интервью и 5 записей `interview_questions` с позициями 1–5.
7. Вернуть `201`.

### GET /api/interviews

- **Назначение:** история (UC-006) и проверка, есть ли незавершённое интервью на главном экране.
- **Авторизация:** нужна.
- **Параметры запроса:** `status` = `COMPLETED` (по умолчанию) или `ACTIVE` (`CREATED` и `IN_PROGRESS`).
- **Пример ответа — 200:**

```json
{
  "items": [
    { "id": "6f1c2b0e-8a3d-4c1e-9d4f-2a7b5c9e1f30", "status": "COMPLETED", "directionName": "Backend-разработка (Python)", "levelName": "Junior", "finishedEarly": false, "completedAt": "2026-11-05T10:52:00Z", "totalScore": 7.4 }
  ]
}
```

- **Коды ошибок:** `400 VALIDATION_ERROR` — недопустимый `status`.
- **Логика backend:** вернуть только интервью текущего пользователя с нужным статусом, новые сверху. Пагинации в MVP нет.

### GET /api/interviews/{id}

- **Назначение:** данные для шапки экрана интервью: позиция, уровень, прогресс.
- **Авторизация:** нужна.
- **Пример ответа — 200:**

```json
{ "id": "6f1c2b0e-8a3d-4c1e-9d4f-2a7b5c9e1f30", "status": "IN_PROGRESS", "directionName": "Backend-разработка (Python)", "levelName": "Junior", "totalQuestions": 5, "answeredCount": 2 }
```

- **Коды ошибок:** `403`, `404` — проверка доступа.
- **Логика backend:** проверка доступа; `answeredCount` — число ответов в `answers`.

### GET /api/interviews/{id}/questions/current

- **Назначение:** вопрос, на который пользователь ещё не ответил (UC-004, FR-5.5.2, FR-5.5.4).
- **Авторизация:** нужна.
- **Пример ответа — 200:**

```json
{ "position": 3, "totalQuestions": 5, "questionId": "a2d4e6f8-1b3c-4d5e-8f9a-0b1c2d3e4f5a", "text": "Чем список отличается от кортежа в Python?" }
```

**Коды ошибок**

| Код | `error.code` | Когда |
| --- | --- | --- |
| 409 | `INTERVIEW_COMPLETED` | Интервью завершено — фронт открывает результаты |
| 409 | `ANALYSIS_FAILED` | Ответы есть на все вопросы, но часть не проанализирована; их id — в `details.failedAnswerIds` |

**Что сохраняется:** при первом вызове статус меняется с `CREATED` на `IN_PROGRESS` и записывается `started_at`.

**Логика backend**

1. Проверка доступа. Статус `COMPLETED` — `409 INTERVIEW_COMPLETED`.
2. Статус `CREATED` — перевести в `IN_PROGRESS`.
3. Вернуть вопрос с наименьшим `position`, на который нет ответа.
4. Таких нет, но есть ответы со статусом `FAILED` — `409 ANALYSIS_FAILED`.

### POST /api/interviews/{id}/answers

- **Назначение:** сохранить ответ и получить его анализ (UC-004, FR-5.5.3, FR-5.6.1 – FR-5.6.4).
- **Авторизация:** нужна.

**Параметры запроса**

| Поле | Тип | Обязательное | Правила |
| --- | --- | --- | --- |
| `questionId` | UUID | Да | Текущий вопрос интервью |
| `answerText` | string | Да | От 1 до 4000 символов после обрезки пробелов [Предложение по длине] |

**Пример запроса**

```json
{ "questionId": "a2d4e6f8-1b3c-4d5e-8f9a-0b1c2d3e4f5a", "answerText": "Список изменяемый, кортеж нет..." }
```

**Пример ответа — 201**

```json
{
  "answerId": "c7e9a1b3-5d7f-4a9b-8c1d-3e5f7a9b1c2d",
  "analysisStatus": "DONE",
  "analysis": {
    "score": 8,
    "criteria": { "accuracy": 9, "completeness": 7, "clarity": 8 },
    "strengths": ["Верно названо главное отличие"],
    "weaknesses": ["Нет примера использования"],
    "recommendation": "Добавьте пример, когда кортеж удобнее списка"
  },
  "interviewStatus": "IN_PROGRESS",
  "nextPosition": 4
}
```

Разбор отдаётся сразу, чтобы фронт мог показать оценку (FR-5.6.4). Показывать её сразу или только в результатах — [Вопрос 1](#вопросы-к-команде). После пятого ответа `interviewStatus = COMPLETED`, `nextPosition = null`.

**Коды ошибок**

| Код | `error.code` | Когда |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Ответ пустой или длиннее 4000 символов |
| 409 | `INTERVIEW_COMPLETED` | Интервью завершено |
| 409 | `NOT_CURRENT_QUESTION` | Вопрос не текущий или на него уже есть ответ |

Сбой LLM — не ошибка запроса: ответ сохраняется, `analysisStatus = FAILED`, `analysis = null`.

**Что сохраняется:** запись в `answers`, после анализа — оценка, критерии, сильные и слабые стороны, рекомендация.

**Логика backend**

1. Проверка доступа; статус интервью должен быть `IN_PROGRESS`.
2. Проверить длину ответа и что `questionId` — текущий вопрос.
3. Сохранить ответ со статусом `PENDING` и закоммитить — ответ не потеряется при сбое LLM.
4. Отправить в LLM текст вопроса, эталонный ответ (если есть), уровень и ответ. Таймаут — 30 секунд [Предложение].
5. Проверить ответ LLM: `score` — целое 0–10; `criteria` — `accuracy`, `completeness`, `clarity`, каждый 0–10 (FR-5.6.2); `strengths` — 1–3 пункта, `weaknesses` — 0–3 пункта, `recommendation` — 1–300 символов. Ошибка, таймаут или ответ не по схеме — один повтор.
6. Успех — сохранить разбор, статус `DONE`; неудача — статус `FAILED`.
7. Если это пятый ответ и все пять в статусе `DONE` — [завершить интервью](#завершение-интервью).
8. Вернуть `201`.

### POST /api/interviews/{id}/answers/{answerId}/retry

- **Назначение:** повторить анализ ответа со статусом `FAILED`.
- **Авторизация:** нужна.
- **Пример ответа — 200:** такой же объект, как у отправки ответа.
- **Коды ошибок:** `404 ANSWER_NOT_FOUND`; `409 ANALYSIS_NOT_FAILED` — анализ уже выполнен.
- **Логика backend:** проверка доступа; ответ из этого интервью и в статусе `FAILED`; выполнить шаги 4–7 отправки ответа.

### POST /api/interviews/{id}/complete

- **Назначение:** досрочно завершить интервью (UC-008, FR-5.5.5).
- **Авторизация:** нужна.
- **Параметры запроса:** нет.
- **Пример ответа — 200:** `{ "id": "6f1c2b0e-...", "status": "COMPLETED", "finishedEarly": true, "totalScore": 6.5 }`

**Коды ошибок**

| Код | `error.code` | Когда |
| --- | --- | --- |
| 409 | `NO_ANSWERS` | Нет ни одного ответа ([Вопрос 4](#вопросы-к-команде)) |
| 409 | `ANALYSIS_FAILED` | Есть непроанализированные ответы; их id — в `details.failedAnswerIds` |

**Логика backend**

1. Проверка доступа. Интервью уже завершено — вернуть `200` с текущими данными, ничего не меняя.
2. Ответов нет — `409 NO_ANSWERS`. Есть ответы не в статусе `DONE` — `409 ANALYSIS_FAILED`.
3. [Завершить интервью](#завершение-интервью) с `finished_early = true`.

### Завершение интервью

Общая логика: вызывается автоматически после пятого проанализированного ответа и из досрочного завершения.

1. `status = COMPLETED`, записать `completed_at`, `finished_early` — по способу завершения.
2. `total_score` — среднее оценок всех проанализированных ответов, округлённое до одного знака (FR-5.7.1).
3. Создать `interview_feedback` со статусом `PENDING`. Отправить в LLM вопросы, ответы, оценки и уровень; ждать `summary` (2–3 предложения), до 3 сильных тем, до 3 тем для повторения и до 3 рекомендаций (FR-5.7.2).
4. `level_verdict` backend считает сам по итоговому баллу: от 7.5 — соответствует уровню, от 5.0 до 7.4 — частично, ниже 5.0 — не соответствует [Предложение].
5. Ошибка LLM — статус `FAILED`; интервью при этом остаётся завершённым.
